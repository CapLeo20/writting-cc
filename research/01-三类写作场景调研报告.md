# 调研报告：让 Claude Code 的三类写作更"说人话"

- 面向：经济学博士生，以中文进行经济学、金融学研究与论文写作
- 日期：2026-10-18
- 范围：三类写作场景已有的模板、写作经验、可复用的 Claude Code 工具，以及我的评价和落地建议

| 场景 | 读者 | 目标 |
| --- | --- | --- |
| 一、日常阅读学习时的回复 | 你本人 | 清楚、少格式、用常用术语，方便理解和协作 |
| 二、论文学术写作 | 编辑、审稿人、同行 | 准确之外还要有经济学叙事，能吸引人 |
| 三、agent 之间的对话与交接 | 另一个 agent 或新会话 | 准确、可核对、省 token |

## 0. 先说结论

**场景一：日常回复**

1. 最合适的落地方式是 Claude Code 的**自定义输出风格（output style）**。它是一份规则文件，对每一次回复生效，不需要每次重复要求。
2. 规则内容可以从三类现成材料里取：Anthropic 官方的格式控制写法；中文"去模板化"规则 Humanizer-zh；阮一峰《中文技术文档的写作规范》和余光中对欧化中文的批评。
3. 有一块没有现成模板：**经济学中文术语约定**。需要自建一张术语表，以国内常用教材的译名为准。

**场景二：论文写作**

1. 英文经济学写作经验已经很成熟，核心文献十来篇，结论高度一致：只讲一个核心贡献、开门见山、引言用固定结构、结果要讲经济含义。
2. "故事性"主要靠结构，而不是文采：一个有张力的问题 → 为什么难 → 本文怎么解决 → 发现了什么 → 意味着什么。故事集中在引言和结论，正文保持平实。
3. 已有一个质量较高的开源 skill：[hanlulong/econ-writing-skill](https://github.com/hanlulong/econ-writing-skill)，综合了 50 多份写作指南。但它按 AER/QJE 的英文惯例写，和中文期刊的结构习惯有冲突，适合当底稿改写，不宜直接用于中文论文。
4. 中文期刊公开的系统写作指南很少。最有用的是北大《经济学（季刊）》的"论文可读性改进建议"和 Cochrane 写作指南的中文译本。学习顶刊风格，较可行的办法是自建 10–20 篇范文库，让 Claude 逐段标注"这一段在做什么"，再提炼成风格卡。
5. "写得好会影响评价"有实验证据：Feld、Lines 和 Ross（2024，JEBO）的随机实验显示，经过语言编辑的博士生论文，被经济学家评为学术质量更高，也更可能被会议接收。

**场景三：agent 交接**

1. Anthropic 工程博客已经给出比较完整的做法：委派任务时写清目标、输出格式、可用工具和信息来源、任务边界；长任务用"结构化状态文件（JSON）+ 自由文本进度笔记 + git 记录"交接；子 agent 只回传 1,000–2,000 token 的浓缩摘要。
2. 交接文档要的是"可核对"，不是"好读"：区分已核实和未核实的内容，写明路径和命令，记录失败过的尝试，写清什么算完成。

## 2. 场景一：日常阅读与学习时的回复

### 2.1 要解决的问题

你的要求是：清楚，不用生僻生硬的词，格式少，用约定俗成的高频术语。对应到 AI 回复的常见毛病，主要有五类：

1. **格式过度**：层层标题、到处加粗、一行一个短要点，把连贯的道理切碎。
2. **模板化表达**："不是 X，而是 Y"、"值得注意的是"、"深入探讨"、"赋能"、凑三项的排比、结尾升华。
3. **欧化中文**："对……进行分析"、"作出贡献"、一句话里好几个"的"、被字句堆叠、长串名词。
4. **术语不统一**：自造译名，中英文混用没有规律，同一概念前后说法不同。
5. **太长**：先复述问题、再铺垫、最后总结，真正的答案只占一半。

### 2.2 现成资源

**（1）Anthropic 官方：控制回复格式的写法【原文】**

来源：[Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)。官方给了四条方法：

- 告诉它该怎么写，而不是不许怎么写。例如用"回复由连贯的段落组成"代替"不要用 markdown"。
- 用 XML 标签标明格式要求。
- 提示词本身的格式会影响输出格式。提示词里少用 markdown，回复里的 markdown 也会变少。
- 需要精细控制时，写一段详细的格式规则。官方给了一个示例 `<avoid_excessive_markdown_and_bullet_points>`：长回答用完整段落；只有真正并列的条目或用户要求时才用列表；不要输出一串过短的要点。

官方同时提醒：较新的模型本身格式就少，这类强约束可能把内容确实需要的结构也压掉。

**（2）Anthropic 官方：控制长度【原文】**

来源：[Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)。要点：

- 这一代模型默认回复偏长，effort 参数控制的是"想多少"，不是"说多少"，要直接写长度要求。
- 官方示例："Keep responses focused, brief, and concise. Keep disclaimers and caveats short, and spend most of the response on the main answer. When asked to explain something, give a high-level summary unless an in-depth explanation is specifically requested."
- 写成文件的报告也偏长，官方建议加一句："长度匹配任务需要，不加填充章节、重复摘要和套话。"
- 汇报节奏：结束时先说结果，第一句回答"发生了什么"或"发现了什么"，细节放后面。

**（3）Claude Code 的输出风格（output styles）【原文】**

来源：[Output styles 文档](https://code.claude.com/docs/en/output-styles)。这是场景一最对口的机制：

- 输出风格是一组对整个会话每次回复都生效的指令，管角色、语气和格式。
- 内置 Concise 风格：第一句给结论，去掉铺垫、过程叙述和结尾复述，简单问题一到三句话答完。
- 可以自己写：在 `~/.claude/output-styles/`（对所有项目生效）或项目内 `.claude/output-styles/` 放一个 Markdown 文件，用 `/output-style 名字` 切换。
- `keep-coding-instructions: true` 表示保留 Claude Code 原有的编程行为，只改沟通方式。你既要它写代码跑回归，又要它说话清楚，应该打开这一项。
- 输出风格对主对话生效，对子 agent 不生效（fork 除外）。所以场景三的写法需要另外规定。

**（5）中文写作规范**

- 阮一峰《[中文技术文档的写作规范](https://github.com/ruanyf/document-style-guide)》【原文】。和你的需求高度吻合的几条：
  - 不含标点的单句，或逗号隔开的句子成分，尽量在 20 字以内；20–29 字可以接受；30–39 字要求语义明确；超过 40 字不能接受。
  - 多用简单句和并列句，少用复合句。
  - 同一个意思尽量用肯定句表达，避免双重否定。
  - 尽量用主动语态。
  - 不用冷僻、生造或文言的词，用现代汉语的常用说法。
  - "其、该、此、这"等代词要指代明确。
  - 名词前不堆过多形容词。
  - 中英文之间加空格。
- 余光中《怎样改进英式中文？——论中文的常态与变态》和《论的的不休》【摘要】：批评"进行""作出"这类弱化动词，批评名词泛滥和"的"字滥用。这两篇是中文界讨论欧化句式最常被引用的文章。
- [中文文案排版指北](https://github.com/sparanoid/chinese-copywriting-guidelines)【原文】：只管排版（空格、标点、全半角），可以作为排版规则的依据。

**（6）经典写作书里和"解释清楚"相关的原则【摘要】**

- Pinker《The Sense of Style》：坏文章最主要的成因是"知识的诅咒"，即作者忘了读者不知道自己知道的东西。Pinker 提倡"经典风格"，像指给读者看一样写，少用 somewhat、relatively 一类含糊限定。
- Joseph Williams《Style: Lessons in Clarity and Grace》：让人物做主语，让动作做动词；句首接旧信息，句尾放新信息。
- René Stulz（前 *Journal of Finance* 主编）给 JFE 作者的建议：摘要、引言和结论要清楚到读给 MBA 班听也能懂。【判断】这条很适合当场景一的标准：Claude 给你讲一篇论文，应该让一个学过中级计量的人能听懂。

### 2.3 评价与取舍【判断】

1. **现成的去 AI 味工具大多是"改已有文本"，场景一要的是"一开始就写对"。** 所以应该把规则精简后放进输出风格，而不是每次回复后再跑一遍改写。
2. **规则不能绝对化。** "禁止被动""删掉所有副词"这类规则放进经济学语境会伤准确性。Humanizer-zh 的优先级（先保信息和确定程度，再改表达）更合适。
3. **少格式不等于零格式。** 回归结果对比、变量定义、操作步骤，用表格或编号更清楚。规则应该是"默认用段落，确实是并列条目再用列表"。
4. **术语没有现成工具，需要自建。** 建议以国内最常用的教材译名为准，例如伍德里奇《计量经济学导论》中译本、陈强《高级计量经济学及 Stata 应用》、安格里斯特和皮施克《基本无害的计量经济学》中译本。第一次出现写"双重差分（DID）"，之后统一用一种说法。没有通行中文译名的术语，直接用英文，不要自造。

### 2.4 规则草案（下一步可直接做成输出风格）

下面是我根据以上材料拟的初稿，供你修改：

```text
你在和一位经济学博士生合作阅读论文、讨论实证方法。回复的目标是让对方快速看懂。

1. 第一句直接回答问题或给出结论，细节放后面。不复述问题，不写开场白，不写结尾总结。
2. 用连贯的段落写。只有真正并列的条目、步骤或需要对比的数字才用列表或表格。少用粗体，不用多级标题。
3. 用常用说法，不用生僻词、生造词和文言词。一句话尽量不超过 30 个字。
4. 术语用国内教材通行的中文译名，第一次出现附英文或缩写，例如"双重差分（DID）"。没有通行译名的直接用英文。同一概念前后说法一致。
5. 讲实证论文时按这个顺序：研究问题 → 识别策略（用的什么变异）→ 主要结果（带量级）→ 关键假设和可能的问题。
6. 系数要翻译成经济含义，例如"相当于样本均值的 X%"。
7. 不夸大：相关不说成因果，"可能"不说成"一定"，原文的限定条件要保留。不确定的地方直说不确定。
8. 避免"不是……而是……"、"值得注意的是"、"深入探讨"、"赋能"、凑三项排比、结尾升华这类套话。
9. 少用"进行""作出"加名词的结构，能用动词就用动词。
10. 长度匹配问题：简单问题几句话答完；需要展开时也只写必要内容。
```

## 3. 场景二：经济学、金融学论文写作

### 3.1 核心文献清单

**第一梯队：几乎所有经济学写作资源清单都会列的**

| 作者 | 文献 | 要点 |
| --- | --- | --- |
| John Cochrane（芝大布斯/胡佛研究所，金融经济学） | *Writing Tips for Ph.D. Students*（2005）【摘要】 | 先想清楚论文唯一的核心贡献，并用一段话写出来；摘要 100–150 词，只讲这个贡献，不引文献；引言开门见山，不要"清嗓子"（大段讲问题多重要），不超过 3 页；"路线图"段可省；实证部分从主要结果讲起。**有中文译本《经济学博士生论文写作指南》**，放在 Cochrane 个人网站上 |
| Keith Head（UBC） | *The Introduction Formula*【摘要】 | 引言五步：Hook（吸引读者）→ Question（本文做什么）→ Antecedents（只引推动叙事的关键前作，礼貌指出其不足）→ Value-added（约三点贡献，Head 认为这是说服审稿人最重要的一段）→ Roadmap（要针对本文定制，点出关键节点）。Hook 的四种来源：Y 很重要（涨跌影响人的福利）、Y 令人困惑、Y 有争议、Y 规模大或很常见 |
| Jesse Shapiro（哈佛） | *Four Steps to an Applied Micro Paper*（2022）【摘要】 | ① 动手研究前先写一篇"理想引言"，只有假想的结果能让你满意才值得做；② 研究从最不清楚的部分开始，用引言当指南；③ 正文写给"机器人读者"：平实、清楚、线性，不推销；④ 拿到真实结果后重写引言 |
| Deirdre McCloskey | *Economical Writing*（第 3 版，2019，芝大出版社）【摘要】 | 35 条规则，从篇章结构到段落、句子、用词。被拿来和 Strunk & White 相提并论 |
| David Evans（全球发展中心） | [How to Write the Introduction of Your Development Economics Paper](https://www.cgdev.org/blog/how-write-introduction-your-development-economics-paper)【摘要】 | Evans 把一批顶刊发展经济学论文的引言逐段画了结构图，归纳出：动机（1–2 段）→ 研究问题（1 段）→ 实证方法 → 详细结果（3–4 段，篇幅最大）→ 相对文献的增量 → 路线图 |

| Marc Bellemare（明尼苏达） | 书 *Doing Economics*（MIT 出版社，2022）；博客 *The Conclusion Formula*、*The Middle Bits Formula*【摘要】 | 应用经济学论文的逐节写法，包括结论和正文中间部分的"公式" |
| Michael Kremer（诺奖得主） | *Writing Papers: A Checklist*【摘要】 | 写作自查清单 |

**理论和模型写作**

- Paul Krugman, *How I Work*（1993）【摘要】：四条研究规则：听领域外聪明人的意见、质疑问题本身、敢于"犯傻"、尽量简化。Krugman 把模型看作隐喻，用最简单的模型讲清一个想法。
- Edward Glaeser, *How to Write a (Low-Brow) Theory Paper*：据 econ-writing-skill 的转述，核心是"从一个例子开始"【摘要】。
- Hal Varian, *How to Build an Economic Model in Your Spare Time*：从一个具体现象出发，先建最简单的模型。

**金融学**

- René Stulz（前 *Journal of Finance* 主编），*JFE Tips for Authors*【摘要】：摘要、引言和结论要清楚到能读给 MBA 班听；正文能简单解释就不用技术语言；要引用最新的相关文献，审稿人常因作者不了解最新文献而否定论文；不贬低别人的工作。
- Bill Schwert 维护的 JFE 投稿建议页（billschwert.com/jfe/tips.htm）【摘要】。
- Michael Weisbach（俄亥俄州立大学金融学教授），*The Economist's Craft*（普林斯顿大学出版社，2021）【摘要】：从选题、论文各部分的结构到投稿后的流程。
- Ben Jacobsen, *Some Research and Writing Tips Part 2: Writing*【摘要】：打印出来读，读起来和屏幕上不一样；读顶刊时既看别人写了什么，也看怎么写；先写摘要和引言，能逼自己想清楚什么最重要。
- *Journal of Finance* 格式指南（2017 版）【摘要】：摘要不超过 100 词，引言最后一段介绍全文结构。

**"讲故事"相关**

- Joshua Schimel, *Writing Science*（牛津大学出版社，2012）【摘要】：主张科学论文要讲故事，给出 OCAR 结构：Opening（开场）、Challenge（挑战）、Action（行动）、Resolution（解决）。
- McCloskey, *The Rhetoric of Economics*（1985）和 *If You're So Smart: The Narrative of Economic Expertise*（1990）【摘要】：经济学家其实像诗人一样用隐喻（例如"人力资本"），像小说家一样讲故事，只是自己没意识到。
- 【判断】Ariel Rubinstein 的 *Economic Fables* 和 Dani Rodrik 的 *Economics Rules* 都把模型比作"寓言"，适合用来理解"模型就是故事"这层意思。

**证据：写作质量影响评价**

Feld、Lines、Ross，"Writing Matters"，*JEBO* 217（2024）【摘要】。实验请专业编辑修改 30 篇经济学博士生论文的语言，每位经济学家评 5 篇原稿和 5 篇编辑稿（不会看到同一篇的两个版本）。发表版的结果：经济学家对编辑稿的整体评价高 0.2 个标准差，接收为会议论文的概率高 8.4 个百分点，认为能发好期刊的概率高 4.1 个百分点；写作专家认为编辑稿写得更好，高 0.6 个标准差。原稿写得越差，编辑带来的提升越大。（工作论文版和发表版数字有出入，引用前请核对发表版。）

### 3.2 这些资料的共识【判断】

1. **只讲一个核心贡献，先于一切。** Cochrane 和 Shapiro 都要求动笔前能用一段话说清。
2. **倒金字塔结构。** 每一层都先讲结论：摘要先于引言，引言先于正文，每段先于细节。
3. **写发现了什么，不写研究了什么。** Cochrane 的反例是"我分析了高管薪酬数据，发现了许多有趣的结果"。
4. **文献为故事服务。** 只放推动叙事的 5–10 篇，用"然而"引出本文。不要"张三发现 X，李四发现 Y"式罗列。
5. **讲经济显著性。** 系数要翻译成读者能感受的量级：占均值的百分比，相当于多大的政策效果。
6. **引言反复重写。** 研究前写一遍，拿到结果后按事实重写，之后每次修改都过一遍。
7. **故事集中在引言和结论，正文平实。** 这一点对你的需求很关键。Shapiro 明确说正文写给"机器人读者"，不推销。故事性不等于全文修辞化。

### 3.3 "故事性"具体指什么【判断】

故事性不是辞藻，而是**张力加解决**。Head 的四种 Hook 就是四种张力来源，Schimel 的 OCAR 是同一件事的通用版本。

经济学论文常见的几种叙事骨架如下。例子是我根据对这些经典论文的了解归纳的，用作写作参考前请核对原文。

| 骨架 | 张力来源 | 可参考的例子 |
| --- | --- | --- |
| 困惑型 | 现实与理论或常识的预测不一致 | Card & Krueger（1994，AER）最低工资研究：先摆出传统理论的明确预测（提高最低工资会减少就业），再用新泽西和宾夕法尼亚的自然实验检验 |
| 大问题型 | 一个根本性问题 | Acemoglu、Johnson、Robinson（2001，AER）开篇直接问：各国人均收入差距巨大的根本原因是什么？ |
| 概念型 | 提出一个新概念，统一解释一组现象 | Akerlof（1970，QJE）用二手车市场的"柠檬"讲清信息不对称；周黎安（2007，《经济研究》）用"晋升锦标赛"解释地方官员激励与经济增长 |
| 事实优先型 | 先摆出一个新的、有冲击力的事实 | Chetty、Hendren、Kline、Saez（2014，QJE）拿"机会之地"这一流行说法对照美国各地代际流动性数据；econ-writing-skill 引述的演讲建议里提到，Fama 讲论文常以"请看表 1"开场 |
| 问题标题型 | 标题本身就是读者关心的问题 | 张军等（2007，《经济研究》）《中国为什么拥有了良好的基础设施？》 |

下面用一个**虚构的例子**对比"列举式"和"叙事式"引言开头。主题和数字都是占位，不是真实研究：

> **列举式：** 近年来，随着数字经济的快速发展，数字金融受到学术界的广泛关注。现有文献从多个角度对数字金融进行了深入探讨。本文基于 2011—2020 年数据，运用双重差分方法，研究数字金融对农户创业的影响。本文的边际贡献主要体现在以下三个方面……
>
> **叙事式：** 过去十年，中国县域的移动支付普及率从不到 [X]% 升到 [Y]%，但农户创业率几乎没有变化。如果数字金融真的缓解了融资约束，为什么创业没有跟上？本文利用 [某试点政策] 在县域间先后推开的时间差，发现数字金融确实提高了创业率，但效果集中在 [某类农户]；对 [另一类农户]，信贷可得性改善被 [某种机制] 抵消了。

后者的第一句就是事实，第二句制造张力，第三句给出识别和发现。读者在三句之内知道问题、方法和答案。

### 3.4 中文期刊的语境

**《经济学（季刊）》"论文可读性改进建议"【摘要】**

这是我找到的唯一一份中文顶刊官方发布的写作建议，原文在[期刊投稿系统](https://www.oaj.pku.edu.cn/Journalx_jjx/basicinfo/viewHtmlFile.action?id=23)上，本次无法直接打开。据检索摘要，要点有：

- 题目要反映结论，避免"A 与 B"式写法，可以写成"A 是否导致 B"；有主副标题时，主标题体现一般性的经济学问题。
- 摘要面向非专业读者，主要陈述研究发现，中文 200 字以内。
- 关键词要概括，覆盖面不宜过窄。
- 引言要直入主题，讲清：研究什么问题、为什么有意义、怎么做的（研究设计和数据）、发现了什么、对文献的贡献。文献综述多数情况下可以融入引言。
- 据摘要，页面还提示不要直接写"边际贡献"这几个字。这一条我没能核对原文。
- 另据该刊投稿体例，全文尽量不超过 15,000 字。

**其他中文资料【摘要】**

- 陆毅、孙天阳在《经济学（季刊）》发文讨论"讲好中国故事"：要靠规范的研究方法和平实的经济学语言，不靠宣传式表达；研究局限要如实交代。
- 聂辉华《[如何创作经济学论文？](http://www.niehuihua.com/a/zuopin/xueshulunwen/2016/0602/321.html)》：重点在选题，要求先用一句经济学语言概括自己的问题，再找学者和业内人士验证。
- 网上能检索到的中文经济学写作经验，大多是 Cochrane 等英文指南的译介。国内知名经济学家系统谈论文写作的公开文本很少。

**中英文期刊的结构差异【判断】**

英文顶刊的写作指南普遍主张"文献综述放进引言，不单列一节"。而《经济研究》《管理世界》上常见的结构是：引言、文献综述、制度背景、理论分析与研究假说、研究设计、实证结果、机制分析、异质性分析、结论与政策启示。

所以写中文稿时，**段落内部的写法**（开门见山、讲量级、文献为叙事服务）可以用英文经验，**篇章结构**要以目标期刊近两三年的同领域论文为准，不能照搬英文规则。

还有一点中文论文特有的叙事资源：**制度背景**。很多中文实证论文的故事是"中国某项特有的制度安排（试点、行政边界、渐进改革）提供了检验一个一般性经济学问题的机会"。这和《经济学（季刊）》"主标题体现一般性经济学问题"的建议是一致的：中国情境是识别来源，问题本身要有一般性。

### 3.5 怎样向顶刊作者学风格【判断】

单靠读写作指南学不到具体作者的风格，需要从范文里归纳。建议照 Evans 的做法（给顶刊引言逐段画结构图），让 Claude 帮你做：

1. **选范文。** 目标期刊近 3 年、和你领域接近的论文 10–20 篇。中文可选《经济研究》《管理世界》《经济学（季刊）》，英文可选 AER、QJE、JPE、JF、JFE、RFS 等。
2. **逐段标注。** 让 Claude 给每段标一个"动作"：摆事实、制造张力、提出问题、交代识别、报告结果、讲机制、定位文献、陈述贡献、讲政策含义。统计各类动作的段数和比例。
3. **提炼句式。** 开头句属于哪种类型，怎么报告系数，怎么写贡献，怎么收尾。
4. **生成风格卡。** 每篇一页，写作时作为示例参考。官方文档也说，给示例是控制输出风格最可靠的方法之一。
5. **加入你自己的声音样本。** 给 2–3 段你自己满意的文字，避免最后写出来像别人。

## 4. 场景三：agent 之间的对话与交接

### 4.1 Anthropic 官方经验【原文】

**（1）委派任务要写清四件事**

来源：[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)。

- 每个子 agent 需要：目标、输出格式、可用工具和信息来源的指引、明确的任务边界。
- 早期主 agent 只写简短指令，结果子 agent 误解任务，或者和别的子 agent 重复做同样的搜索。原文："没有详细的任务描述，agent 会重复工作、留下空白，或者找不到必要的信息。"
- 按任务难度分配工作量：简单查事实 1 个 agent、3–10 次工具调用；直接比较 2–4 个子 agent、各 10–15 次调用；复杂研究 10 个以上子 agent，分工明确。

**（2）上下文工程**

来源：[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

- 总原则：找到"能最大化期望结果的最小高信号 token 集合"。
- 子 agent 可以用几万 token 探索，但只回传 1,000–2,000 token 的浓缩摘要。
- 结构化笔记：把进度写进上下文之外的文件（如 NOTES.md、待办清单），上下文重置后再读回来。
- 压缩上下文时，保留架构决策、未解决的问题和实现细节，丢掉冗余内容。
- 提示词要在"合适的高度"：既不写成僵硬的 if-else，也不笼统到默认对方知道背景。

**（3）跨会话的长任务交接**

来源：[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。

- 交接物有四样：功能清单（JSON，每项有描述、测试步骤和 `passes` 字段，后续 agent 只能改 `passes`）、进度日志 `claude-progress.txt`、启动脚本 `init.sh`、git 提交记录。
- 新会话启动顺序：确认工作目录 → 读 git 日志和进度文件 → 读功能清单，选优先级最高的未完成项 → 跑一遍基础测试，先发现上一轮留下的问题。
- 用 JSON 而不用 Markdown 存清单，原因是"模型更不容易误改或覆盖 JSON 文件"。
- 每次只做一项，避免一次铺开太多。

**（4）状态管理**

来源：[Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)。

- 结构化信息（测试结果、任务状态）用 JSON。
- 进度笔记用自由文本。
- 用 git 记录做了什么，并保留可恢复的检查点。
- 新上下文开始时，明确告诉它从哪里读起，例如"先读 progress.txt、tests.json 和 git log"。

**（5）Claude Code 的写法建议**

来源：[Best practices](https://code.claude.com/docs/en/best-practices) 和 [Memory](https://code.claude.com/docs/en/memory)。

- 好的任务说明是自包含的：写明涉及的文件和接口，写明不做什么，以一个端到端的验证步骤收尾。
- CLAUDE.md 每一行都问一句"删掉它会不会让 Claude 出错"，不会就删。单个文件控制在 200 行以内。规则要具体，例如写"用 2 空格缩进"，不写"格式规范"。
- 强调词（如 IMPORTANT）只用在一两行上，处处强调等于没有强调。
- 可以在 CLAUDE.md 里规定压缩时保留什么，例如"压缩时保留修改过的文件清单和测试命令"。

**（6）这一代模型的特点**

来源：[Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)。

- 写进文件的文档偏长，要明确要求"长度匹配任务"。
- 更倾向于委派子 agent，官方建议只在任务大且真正独立时委派，不要用子 agent 复核自己的工作。

### 4.2 社区的交接模板【摘要】

社区有不少 handoff 类 skill，常见结构是：

- 当前状态摘要
- 进行中的工作
- 阻塞和遇到的问题
- 继续工作需要的背景
- 下一步
- 关键决定，并附理由

有一个模板要求每条结论要么已经对照仓库核实，要么明确标注"未核实"。这些都是社区约定，不是官方规范。

### 4.3 提高效率的写法【判断】

综合以上资料，交接和委派文档可以遵守这几条：

1. **固定骨架。** 每次用同样的标题顺序，读者按位置找信息。
2. **分开四类信息：** 事实、已做的决定、假设、待办。混在一起最容易出错。
3. **能定位就定位。** 写绝对路径、行号、命令、提交哈希、数据文件版本，不写"那个回归文件"。
4. **写清什么算完成。** 最好是一个能执行的检查，例如"运行 main.do 后表 3 第 2 列系数为 0.034"。
5. **记下失败的尝试和原因，** 避免下一个 agent 重走。
6. **状态用 JSON 或表格，叙述用短段落。**
7. **术语和变量名只在一处定义。**
8. **数字带单位、样本和来源。**
9. **不写给人看的修饰。** 不铺垫，不客套，不重复总结。
10. **控制长度。** 子 agent 的回报控制在 1,000–2,000 token 左右，详细材料写进文件，回报里只给路径。

### 4.4 模板草案（经济学研究场景）

**委派简报（主 agent 交给子 agent）**

```markdown
## 目标
一句话：要回答什么问题，或要产出什么。

## 背景
只写对方完成任务必须知道的：研究问题、数据位置、已知结论。

## 输入
- 数据：/abs/path/to/data.dta（2011–2020 县级面板，N=…）
- 代码：/abs/path/to/code/main.do
- 参考文献：…

## 要做的
1. …
2. …

## 不做的
- 不改动原始数据
- 不换估计方法，除非发现明显错误并先说明

## 输出格式
- 结论：3–5 句
- 证据：表格或文件路径
- 未核实的地方：逐条列出

## 完成标准
可执行的检查，例如：运行后生成 output/table3.tex，第 2 列系数与日志一致。
```

**交接文档（会话结束时写给下一个会话）**

```markdown
# 交接：<任务名> <日期>

## 当前状态（三句话以内）

## 已完成
- [已核实] 清洗后样本 N=…，见 output/log/clean.log 第 120 行
- [未核实] …

## 进行中
- 正在做：…；卡在：…

## 已做的决定（附理由）
- 聚类到县一级：处理在县级分配

## 试过但失败的
- 用 xx 做工具变量：第一阶段 F 值约 3，弱工具，放弃

## 下一步（按优先级）
1. …

## 运行方式
cd /abs/path && stata -b do main.do
```

## 6. 下一步建议

### 6.1 三个场景对应的 Claude Code 机制

| 场景 | 机制 | 理由 |
| --- | --- | --- |
| 一、日常回复 | 用户级输出风格 `~/.claude/output-styles/econ-plain-zh.md`（打开 `keep-coding-instructions`），配一张术语表 | 对每次回复生效，又不影响写代码、跑回归 |
| 二、论文写作 | 项目级 skill `econ-write-zh`：主文件控制在 500 行内，细节放在 references/ 下，按需读取 | 只在写论文时加载，不占日常对话的上下文 |
| 二、审稿自查 | 单独一个审稿 skill，或直接用 econ-paper-review-skill | 写和审分开，审稿时用新的上下文 |
| 三、agent 交接 | `handoff` 和 `brief` 两个 skill（模板见 4.4），交接约定写进 CLAUDE.md | 输出风格管不到子 agent，需要单独规定 |

### 6.2 仓库结构草案

> 2026-10-18 更新：仓库已改为"来源 → 素材库 → 应用"三层结构，实际目录以根目录 README.md 为准。下面是最初的草案，保留作记录。

```text
writting-cc/
├── research/                    # 调研材料（本文件）
├── output-styles/
│   └── econ-plain-zh.md         # 场景一
├── skills/
│   ├── econ-write-zh/           # 场景二
│   │   ├── SKILL.md
│   │   └── references/
│   │       ├── intro-formula.md       # 引言结构（Head/Evans，按中文期刊调整）
│   │       ├── narrative-patterns.md  # 叙事骨架与例子
│   │       ├── cn-journal-norms.md    # 中文期刊结构与《经济学（季刊）》建议
│   │       ├── zh-style-rules.md      # 中文句子层面的规则
│   │       └── style-cards/           # 范文风格卡
│   ├── handoff/                 # 场景三
│   └── brief/
├── glossary/
│   └── econ-terms-zh.md         # 术语表
└── CLAUDE.md
```

### 6.3 需要你决定的几件事

1. **目标期刊。** 中文主要投哪几本？是否也写英文论文？这决定 `econ-write-zh` 的篇章结构以哪个期刊为准。
2. **声音样本。** 能否提供 2–3 段你自己满意的中文学术文字？用来校准风格，避免写出来像别人。
3. **术语基准。** 术语表以哪本教材的译名为准（伍德里奇中译本、陈强，或你们课题组的习惯）？
4. **范文库。** 是否愿意提供 10–20 篇目标期刊的范文 PDF，用来做 3.5 节的逐段标注和风格卡？
5. **从哪个场景开始。** 我建议先做场景一的输出风格：工作量最小，每天都能用上，也能顺便检验规则写法是否有效。
